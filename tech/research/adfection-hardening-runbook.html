AdFection hardening runbook

Objective

This runbook contains steps to harden personal devices (Kubuntu, Android, Windows, macOS) against AdFection, the spyware technique documented by Citizen Lab on 15 Oct 2026. AdFection is spyware that is delivered to machines through ordinary website ads immediately upon loading.

Vulnerability

AdFection’s technique exploits the standard online advertisement auction process. When a webpage or mobile app has an ad slot and the page containing it loads:

  1. The app/page code running on the user’s device sends a request (bid) to an ad exchange
  2. Advertisers automatically bid for the chance to show that user an ad
  3. The exchange picks the winner and pushes the ad

All of this happens in under a second, hundreds of billions of times a day. Two kinds of middlemen are involved:

  1. Advertisers: buy through a demand-side platform (DSP)
  2. Sites and apps: sell ad slots through a supply-side platform (SSP)

The bid request carries data about the user so buyers can decide whether to bid. Most of it comes from SSP code embedded in the website the user visits or the SDK used to develop the mobile app.

Data typeData source
Mobile advertising IDCore function of Android and iOS
Device detailsSSP code
Precise locationSSP code
IP addressSSP code
Site/app containing the ad slotSSP code
Ad slot specs (format, placement, price, restrictions, security flag, supported APIs, SDK used)SSP code
Ad-firm cookie IDsAd firms’ tracking code in the browser, exchanged between firms by ID syncing
Page cookiesAd’s script, reading cookies set on the page showing the ad
Real IP behind a VPNAd’s script, via WebRTC leak
Phone numberMobile carriers’ “header enrichment”, frequently used for convenience (e.g. letting a site recognize a user by phone number to sign in automatically)

A combination of this information easily allows advertisers to target a single person. And since the winning ad can include code for the target machine to execute within the ad slot, that provides the payload delivery mechanism.

An Israeli ad firm, Discover-Tech, bought ad slots that included the ability to deploy a script. On load, the script gathered information about the client machine, then it to the Discover-Tech server to check it against a list of targets. Non-targets saw a normal ad, while targets got code that loaded a browser exploit that installed Candiru’s spyware. Because the malware only went to chosen devices, the networks serving the ads never saw it).

The payload found in the Al-Jazeera sample machine was a Windows DLL persisting via COM hijack; this lets the malware run in a process the host system classified as legitimate.

Procedure

Linux desktop (Kubuntu)

  1. Automatic security updates: patches known bugs on the user machine; sudo apt install unattended-upgrades && sudo dpkg-reconfigure -plow unattended-upgrades
  2. Block ads and scripts: removes a major distribution channel; install uBlock Origin in Firefox and keep its default filter lists on
    • Chrome doesn’t support full uBlock Origin, only uBlock Lite (can’t run its own filtering logic; its main lists update only with extension updates); prefer to switch primary browsing to Firefox and use Chrome only if sites are broken
  3. Block third-party cookies: removes one way to target a specific device
    • Firefox: Settings → Privacy & Security → Enhanced Tracking Protection → Strict
  4. Turn off JavaScript JIT: JIT speeds up page code by sacrificing security, in that browsers with it on skip interpreting every line of page code and instead convert frequently-run elements into machine code
    • Firefox: browse to about:config and set javascript.options.ion and javascript.options.baselinejit to false
    • Chrome: browse to chrome://settings/content/v8 → Don’t allow sites to use the V8 optimizer
  5. Stop WebRTC IP leaks
    • Firefox, breaks browser video calls: about:config → media.peerconnection.enabled = false
      • This closes every WebRTC leak route at once and removes WebRTC as an attack surface
      • Candiru has exploited a WebRTC zero-day before (CVE-2022-2294)
      • Choose this if you don’t make video calls in the browser
    • Firefox, keeps calls: about:config → set media.peerconnection.ice.default_address_only, media.peerconnection.ice.no_host and media.peerconnection.ice.proxy_only_if_behind_proxy to true
      • This limits which IP addresses WebRTC reveals, but the WebRTC code still runs and can still be attacked
    • Chrome, keeps calls
      • Install WebRTC Leak Prevent, set its IP handling policy to “Disable non-proxied UDP (force proxy)”, and tick “Allow in incognito”; OR
      • Set enterprise policy WebRtcIPHandling = disable_non_proxied_udp in a JSON file under /etc/opt/chrome/policies/managed/
      • Same vulnerability as above; Chrome has no option to turn WebRTC off entirely
  6. Configure system-wide DNS filtering: block advertising domains; set a filtering DNS resolver in NetworkManager for each connection, or run a Pi-hole device on the network

Android

  1. Automatic updates: patches known bugs on the user machine; install system updates, and update Chrome and Android System WebView from the Play Store
  2. Delete the advertising ID: removes one way to target a specific device; Settings → Ads → Delete advertising ID, which removes the ID without issuing a new one
    • Older Android versions use a different path
  3. Configure Private DNS filtering: blocks advertising domains, including in apps; Settings → Network & internet → Private DNS → enter a filtering provider’s hostname
  4. Turn on Advanced Protection (Android 16): turns on Android’s most effective security features; Settings → Security & privacy → Other settings → Advanced Protection → turn on Device protection
    • Blocks sideloading and enables Memory Tagging Extension
  5. Turn off JavaScript JIT in Chrome: Chrome → Settings → Privacy and security → Security → JavaScript optimization and security → turn off the V8 optimizer
    • This is a Chrome setting, so ads shown inside other apps’ web views may not be covered
  6. Cut ad-funded apps: removes exposure to in-app ads; remove or pay for ad-free versions of ad-heavy apps
    • Apps that each showed over 700,000 of these ads include MX Player, Lark Player and Viber

Windows and macOS

Both platforms take the same browser steps as Kubuntu (uBlock Origin in Firefox, third-party cookie blocking, JIT off, WebRTC leak prevention). Platform-specific steps:

Windows

  1. Automatic updates: patches known bugs on the user machine; leave Windows Update and browser auto-update on
  2. Turn off the advertising ID: removes one way to target a specific device; Settings → Privacy & security → General → turn off personalized ads using your advertising ID
  3. Turn off JavaScript JIT in Edge: Edge → Settings → Privacy, search, and services → Security → Enhance your security on the web → Strict
  4. Configure system-wide DNS filtering: blocks advertising domains, including in apps; Settings → Network & internet → your connection → DNS server assignment → a filtering resolver, encrypted if offered

macOS

  1. Automatic updates: patches known bugs on the user machine; leave automatic updates and Rapid Security Responses on
  2. Turn on Lockdown Mode: disables JIT JavaScript compilation in web browsing unless you exempt a site; System Settings → Privacy & Security → Lockdown Mode
    • This acts on Apple’s WebKit engine, so Firefox and Chrome need their own JIT settings

Verification checks

  • WebRTC: with your VPN on, open BrowserLeaks WebRTC and confirm your real public IP doesn’t appear
  • Ad blocking: load a news site that normally shows ads; uBlock’s icon count should be non-zero and ad slots empty
  • DNS filtering: run nslookup mtrtb.com (a Discover-Tech domain); a filtering resolver that lists it returns 0.0.0.0 or no answer, and a normal IP means your list doesn’t cover it
  • Chrome JIT: chrome://settings/content/v8 shows the optimizer disallowed
  • Firefox JIT: about:config shows javascript.options.ion and javascript.options.baselinejit set to false
  • Android: Settings → Ads shows no advertising ID; Advanced Protection shows Device protection on
  • Kubuntu: systemctl status unattended-upgrades reports active

Remaining gaps after hardening

Hardening raises the cost of an attack and cuts the main delivery route; it doesn’t make a targeted device safe.

  1. Zero-days still work: updates only patch known bugs, and turning off JIT narrows the attack surface without closing it; Chrome still runs WebAssembly with the V8 optimizer disallowed
  2. Blocklists lag behind the reality rotating infrastructure: Discover-Tech moved between many domains and also used CloudFront distributions
    • A new domain stays unblocked until a list adds it, and shared CDN hostnames can’t be blocked by name without breaking legitimate sites
  3. In-app ads sit outside browser controls: most ad bids were embedded in apps
    • Browser extensions and JIT settings don’t reach app web views, and an app that uses its own encrypted DNS bypasses system DNS filtering
  4. IP targeting survives ad ID removal: operators can target by IP address alone, and ads collected the device’s public IPv6 address even from non-targets
    • A home IP is stable enough to target without any ad ID
  5. Carrier-side phone number leaks: a separate actor used Discover-Tech infrastructure to exploit mobile carriers’ header enrichment and link ad IDs to phone numbers; it relies on plain HTTP requests, which app web views may still allow
    • The flaw is on the carrier’s side
  6. Other delivery routes: Candiru has also delivered exploits through a compromised news website; ad blocking does nothing against that or against messaging zero-clicks
  7. Profiling without ads: Discover-Tech’s ID-syncing requests fired during site visits even when no ad was served
    • Blocking stops what your lists know about; the rest still builds a profile
  8. No user-side detection: the Al Jazeera infections were confirmed from network logs the organization supplied
    • Nothing in this runbook tells you whether a device is already compromised
